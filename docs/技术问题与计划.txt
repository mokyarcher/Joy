## 问题 1：可视上下文太短，回复「对不上话」

### 现象

微信窗口当前视口里往往只剩最近几条（表情 / 短句 / 图片），如图一只能看到「穿上长袖一个月就回来了」等尾巴。  
没有更早的「出差、海边、晒黑」等信息时，模型无法判断话题，候选回复容易空泛或跑偏。

完整对话其实很长：出差到处跑 → 海边 → 晒黑图 → 「那可太好了」→「去非洲了吗」→「这就是海边」→「穿长袖一个月就回来了」。  
**根因不是模型笨，是送进 API 的画面里根本没有上文。**

### 根因（当前架构）

| 环节 | 现状 |
|------|------|
| 采集 | 只截**当前可见客户区**（PrintWindow / 区域截屏） |
| 识图 | 只解析这一帧里的气泡 |
| 上下文窗口 | `context_messages` 只是「从本帧解析结果里再截取 N 条」，**不能补回屏外历史** |

滚动条上面的消息从未进入内存，所以再调大 `context_messages` 也解决不了「看不见」。

### 目标

在调用识图 / 起草前，尽量凑齐「最近一段完整话题」（例如最近 15～30 条，或最近一次话题转折后的全部可见+缓存消息），而不是仅依赖一屏。

### 可行方案（按推荐顺序）

#### P1-A：会话内存缓存（优先，纯本地，改动小）

- 每次成功识图后，把解析出的消息按「会话 ID（标题/hwnd）」**追加去重**进本地缓存（内存 + 可选落盘）。
- 下次分析时：**缓存历史 ∪ 本帧新消息** 再交给判断/起草。
- 去重键建议：`side + 文本哈希 + 粗略顺序`；图片用「[图片]」占位 + 指纹。
- **优点**：不依赖滚动，立刻缓解「一屏太短」。  
- **局限**：软件启动前 / 清缓存前的更早记录仍没有；换设备无效。

#### P1-B：分析前自动上滚补帧（中等改动）

- 「手动分析 / 自动分析」触发时：在微信客户区模拟滚轮上滚 N 次，每停一帧截屏识图（或本地差分合并气泡），再滚回底部。
- 合并多帧 OCR/识图结果后一次起草。
- **优点**：能补启动前已在屏上滚过的历史。  
- **风险**：打扰用户焦点、滚动动画耗时、群聊刷屏误伤；需「补上下文」开关，默认关或仅手动。

#### P1-C：微信本地库 / 无障碍（暂不推荐作主路径）

- 读微信本地消息库或 UI Automation 拉完整列表。
- **优点**：上下文最完整。  
- **风险**：版本脆弱、合规与隐私敏感、维护成本高。可作为远期调研，不进 MVP。

### 建议落地（问题 1）

1. **先做 P1-A（会话缓存）**：1～2 天可出可用版。  
2. 设置里增加「上下文条数 / 清空本会话缓存」。  
3. 视体验再加 **P1-B 可选「分析前上滚补上下文」**（带次数与超时）。  
4. 文档与 UI 明确：当前能力 =「看见 + 记住本软件运行以来见过的消息」，不是完整微信聊天记录导出。

## 问题 2：分析到出候选全程太慢，体验差

### 现象

点「手动分析」或自动触发后，从截屏到候选气泡出现，体感等待过长，自动模式下更明显。

### 根因（粗分）

当前大致串行：

```text
截屏 → 视觉 API（识图+结构化）→ 判断 LLM → 起草 LLM → 渲染
```

耗时通常集中在：

1. **视觉 API**：上行 JPEG + 模型推理（往往最慢）  
2. **串行两次文本 LLM**（判断 + 起草）  
3. **自动模式**：settle 等待（约 1.8s）+ cooldown，再叠加上述链路  
4. UI 假进度不能缩短真实等待，只会缓解焦虑

### 可行方案

#### P2-A：链路瘦身（优先）✅ 已落地

- **合并判断+起草为一次文本调用**（`analyze_and_draft`）；失败回退分步。  
- 视觉阶段只要「消息列表 JSON」，风格/关系用本地 preset 拼进同一起草 prompt。  
- 预期：少一轮 RTT，体感可砍掉一大块。

#### P2-B：更快的模型与更小的图（部分落地）

- 识图用更小/更快视觉模型；默认 `max_image_side=960`、`jpeg_quality=72`；vision `max_tokens` 降至 1200。  
- 起草用低延迟文本模型；设置里标明「速度档 / 质量档」（待做）。

#### P2-C：流水线与缓存 ✅ 已落地

- 画面指纹未变 → **跳过识图**，直接用缓存 transcript 起草（自动模式尤其有用）。  
- 识图结果按 fingerprint 缓存（最多 12 条）。  
- 自动模式：检测到变化后先本地确认「是否新气泡」，再决定是否打视觉 API（待细化）。

#### P2-D：体验层（不减真实耗时，但改善体感）

- 分阶段真实 ETA（识图中 / 起草中）。  
- 先出「识别摘要」，候选流式追加（若 API 支持 stream）。  
- 自动模式可配置「仅提示有新消息，需点手动分析」以控成本与等待。

### 建议落地（问题 2）

1. ~~**先做 P2-A + P2-C（跳过未变帧识图）**~~：**已完成**。  
2. 加「速度档」：小图 + 快模型。  
3. ~~量一次基线：日志打点~~：已有 `grab_ms / vision_ms(cache|api) / llm_ms / total_ms`。  
4. 自动 settle / cooldown 保持，但可在设置里调，并显示「预计还要 Xs」。

## 总计划（建议里程碑）

| 阶段 | 内容 | 预期效果 | 粗估 |
|------|------|----------|------|
| M1 | 会话消息缓存（P1-A）+ 耗时打点 | 回复贴话题；能看见慢在哪 | 打点已做；P1-A 待做 |
| M2 | 合并 LLM / 跳过未变帧识图（P2-A/C） | 总耗时明显下降 | **已完成** |
| M3 | 速度档（缩图+快模型）+ 自动模式参数可调 | 日常体感可接受 | 缩图默认已调；档位待做 |
| M4 | 可选上滚补上下文（P1-B） | 冷启动也能补更早记录 | 2～3 天（可选） |

### 明确不做（近期）

- 破解 / 直读微信加密库作为主路径  
- 默认全自动上滚（易抢焦点、扰民）

## 验收标准（草案）

**上下文**

- 同一会话连续聊 10+ 条后，即便当前屏只剩 3 条，草稿仍能引用更早话题关键词（如「海边 / 晒黑」）。  
- 清缓存后行为回到「仅当前帧」。

**耗时**

- 记录优化前 `total_ms` 中位数；M2 后目标：**同模型下总耗时下降 ≥ 30%**，或「画面未变再次分析」接近仅起草耗时。
