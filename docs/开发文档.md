# Joy 开发文档

> **Joy** — 开源「看屏副驾」：调用识图 / 视觉 API 读懂屏幕内容，再做判断与辅助动作。  
> 灵感来自 [jev-chat](https://github.com/jev-chat)（对话副驾：读屏 → 判断意图 → 候选回复 → 手动发送）。  
> 文档版本：`0.2` · 日期：2026-09-23 · 状态：设计定稿，进入 M0  
> **相对 jev 的产品差异（已确认）**：识图层必须兼容**国内主流可识图 API**（商汤 SenseNova、Kimi、通义 VL、智谱、硅基流动等），并以 **OpenAI 兼容协议**为一等公民；纯文本模型（如 DeepSeek 官方）用于判断 / 起草。

---

## 1. 一句话定位

**Joy 是一套本地运行的看屏助手内核：截取你自己有权查看的屏幕区域 → 用可配置的识图 / 视觉 API 理解画面 → 按插件化「技能」完成辅助（默认技能：聊天回复副驾），发送与敏感操作永远由人确认。**

与 jev 的核心同构是「采集 → 理解 → 判断 → 起草 → 回填」；与 jev 的关键差异是：

| 维度 | jev-chat | Joy（本项目） |
|------|----------|----------------|
| 采集主路径 | Android 无障碍 / Windows 离线 OCR / macOS 本地模型 | **识图 / 视觉 API 为主**（可降级本地 OCR） |
| 识图生态 | 偏专用判断模型 + 离线 OCR | **国内主流 VL 全家桶 + 自定义 OpenAI 兼容端点** |
| 场景重心 | 聊天 App 回复副驾 | **看屏理解平台**；聊天副驾是第一个技能 |
| 目标平台（首期） | 三端分仓 | **先 Windows**，架构预留多端 |
| 理解接口 | 判断 / 回复 /（可选）视觉分路 | **视觉理解 + LLM 判断/起草** 分卡可配，统一 Provider 层 |

参考资料：

- 组织总览：<https://github.com/jev-chat>
- Android：<https://github.com/jev-chat/jev-chat-jarvis>
- Windows：<https://github.com/jev-chat/jev-chat-windows>
- 官网：<https://chatjevs.com>

## 2. 要解决的问题

看屏幕做决策时，人最费神的往往不是「操作」，而是「读懂」：

- 对方这句话什么意思？有没有风险？该不该回、怎么回？
- 屏幕上某一块 UI / 文档 / 弹窗，关键信息是什么？
- 希望 AI 帮忙，但不想 hook、改包、读数据库，也不想程序自动替自己点「发送 / 支付」。

Joy 把「读懂屏幕」交给可配置的识图 API，把「建议」交给本地编排，把「最终动作」留给用户。

## 3. 硬约束（不可妥协）

以下条款写入代码与 README，视为产品底线：

1. **只处理本机、用户自己有权查看的画面。** 不用于监视他人、不绕过权限。
2. **不 hook、不注入、不读第三方 App 数据库 / 进程内存、不调私有接口。** 采集 = 窗口 / 区域截图（或系统允许的公开辅助能力）。
3. **不自动发送消息；不碰转账、红包、支付、收款。** 默认技能只「填入输入框 / 复制到剪贴板」。
4. **密钥只存本机**（环境变量或系统凭据库），不进仓库、不进日志；报错脱敏。
5. **无自建中间服务器。** 网络请求只打用户配置的 API；项目不收集聊天内容。
6. **截图默认仅内存流转**；调试落盘必须显式开关，且默认关闭、不进发布包常规路径。
7. **开源协议拟用 MIT**；商用须保留 LICENSE / NOTICE，不得冒充 jev-chat 官方。

## 4. 产品范围

### 4.1 MVP（v0.1）— Windows 聊天副驾

对标 jev-windows 的使用闭环，但理解层以视觉 / 识图 API 为主：

1. 用户指定或自动附着目标窗口（首期：微信 Windows 4.x，可配置窗口标题 / 类名）。
2. 周期或事件触发截取窗口客户区（WGC / BitBlt 择优）。
3. 将裁剪后的消息区域图片发给 **Vision Provider**，得到结构化对话：`{ title, messages[{side, name?, text}] }`。
4. **Analyze Provider** 输出：意图摘要、风险 / 紧张度、建议动作、是否宜立刻回复。
5. **Draft Provider** 生成 3 条候选回复并（可选）排序打分。
6. 悬浮窗展示结果；用户点击「填入」→ 粘贴到目标输入框（不发送）。
7. 设置页：各 Provider 的 Base URL / Key / Model、采集开关、关系与说话风格、上下文条数。

### 4.2 非目标（v0.1 明确不做）

- Android / macOS 客户端（架构预留，实现后置）
- 自动发送、自动点赞、自动加好友
- 读取微信本地数据库 / 解密聊天记录
- 云端账号体系、项目方中转代理
- 复杂知识库语义检索（可后置；MVP 可用简单「关系 + 风格」文本配置）

### 4.3 后续技能（插件化，v0.2+）

同一套「截图 → 识图」内核上挂不同 Skill：

| Skill ID | 说明 |
|----------|------|
| `chat_copilot` | 默认：意图 + 候选回复（MVP） |
| `screen_summarize` | 任意窗口一句话摘要 |
| `form_assist` | 读表单字段，生成填写建议（仍需用户确认粘贴） |
| `ui_locate` | 描述控件位置（辅助无障碍 / 测试，慎用自动化点击） |

## 5. 总体架构

```
┌─────────────────────────────────────────────────────────────┐
│                        Joy Desktop (UI)                      │
│   Overlay 悬浮窗 · Settings · Session 列表 · Debug Viewer     │
└───────────────────────────┬─────────────────────────────────┘
                            │ IPC / 进程内调用
┌───────────────────────────▼─────────────────────────────────┐
│                      joy-core（编排引擎）                      │
│  Capture → VisionParse → Diff/Dedupe → Skill.analyze → UI    │
└───┬───────────┬───────────────┬───────────────┬─────────────┘
    │           │               │               │
┌───▼───┐ ┌─────▼─────┐ ┌───────▼───────┐ ┌─────▼─────┐
│capture│ │ providers │ │    skills     │ │   fill    │
│ WGC   │ │ vision    │ │ chat_copilot  │ │ clipboard │
│ region│ │ llm       │ │ (extensible)  │ │ SendInput │
│ hash  │ │ rank      │ │               │ │ (no send) │
└───────┘ └───────────┘ └───────────────┘ └───────────┘
```

### 5.1 分层说明

| 层 | 职责 | 可替换性 |
|----|------|----------|
| **Capture** | 找到窗口、截帧、裁剪消息区、帧哈希去重 | 按 OS / 按 App 适配 |
| **Vision** | 图 → 结构化文本（对话气泡、UI 文案） | OpenAI Vision / 通义 / Gemini / 自定义；可插本地 OCR 兜底 |
| **Providers** | 统一 OpenAI 兼容客户端；**国内 VL 预设表**；重试、超时、脱敏日志 | 换预设 / 自定义 Base URL 即可 |
| **Skills** | 业务：判断题、提示词、候选条数、是否需要填入 | 插件 |
| **Fill** | 剪贴板 / 模拟粘贴到输入框 | 永不止步到「发送」 |
| **UI** | 悬浮窗与设置 | 与 core 解耦，便于无头调试 |

### 5.2 与 jev 三段式对齐（聊天技能）

参考 jev-windows 的「判断 → 起草 → 排序」：

```
新对方消息（或手动触发）
  → Vision 得到最近 N 条结构化消息
  → Analyze：意图 / 需求 / 建议动作 / 风险分
  → Draft：带「判断小抄」写 3 条候选
  → Rank（可选）：给候选排序或胜出概率
  → Overlay 展示 → 用户点「填入」
```

失败降级：

- Vision 失败 → 提示用户；可选本地 OCR 兜底（若已启用）
- Analyze 失败 → 「盲起草」（仅上下文）并标注降级
- Rank 失败 → 按模型返回顺序展示

### 5.3 为何首期以识图 API 为主（相对离线 OCR）

jev-windows 因微信 4.x 自绘、UIA 几乎无树，采用 **WGC + RapidOCR + 气泡颜色启发式**。该路径稳、隐私好，但：

- 气泡分边、灰字过滤、群聊人名挂靠等启发式脆弱，主题 / 版本一变易碎；
- 多 App 适配成本高。

Joy 用视觉模型直接「读图出结构」，换 App 时优先改 **区域裁剪提示 + Prompt**，而不是大量像素启发式。代价是：**出网与按次计费**，因此必须：

- 仅在「对方新消息 / 手动分析」时调用；
- 支持缩小裁剪区域、降分辨率、JPEG 质量档；
- 设置里清晰展示「本次将上传裁剪图到某某 API」。

本地 OCR 作为可选 Provider，不作为 MVP 阻塞项。

## 6. 技术选型（建议）

| 项 | 建议 | 理由 |
|----|------|------|
| 语言 | **Python 3.11+** | 与 jev-windows 生态接近，Vision/LLM SDK 成熟，打包生态可行 |
| UI | **PySide6 / Qt** | 置顶悬浮窗、跨 DPI 成熟 |
| 截屏 | **Windows Graphics Capture (WGC)** 优先，BitBlt 兜底 | 可截 GPU 合成窗、被遮挡窗（与 jev-windows 同类） |
| 配置 | `config.json`（无密钥）+ 系统环境变量 / Windows Credential | 密钥不落明文文件 |
| 打包 | PyInstaller / 后续考虑 Nuitka | 发布 zip + exe |
| 测试 | pytest + 固定截图 fixture | Vision 用 mock HTTP |
| 协议 | MIT | 与 jev 友好、便于二次开发 |

若后续强性能 / 单文件体积敏感，可将 Capture + Fill 拆成 Go/Rust 子进程；MVP 不必提前拆。

## 8. 核心数据模型（草案）

```python
# 伪代码示意

@dataclass
class ChatMessage:
    side: Literal["me", "other", "system"]
    text: str
    name: str | None = None      # 群聊发言人
    ts: datetime | None = None

@dataclass
class ScreenContext:
    app_id: str                  # e.g. "wechat_win"
    title: str                   # 会话名 / 窗口标题
    messages: list[ChatMessage]
    raw_image_b64: str | None    # 默认不落盘；仅本次请求内存
    source: Literal["vision_api", "ocr_local", "manual"]

@dataclass
class Analysis:
    intent: str
    need: str
    suggested_action: str
    risk: int                    # 0–9
    should_reply_now: bool
    confidence: float | None
    degraded: bool = False

@dataclass
class Candidate:
    text: str
    score: float | None          # 排序概率
    recommended: bool = False
```

Vision Prompt 要求模型 **只输出 JSON**（附 schema），解析失败则重试一次或降级。

## 9. Provider 配置设计

### 9.1 一等需求：国内识图 API 兼容

Joy **不以某一家模型为中心**。识图层的设计目标是：

> **一套 OpenAI 兼容的 Vision 客户端 + 厂商预设表**，覆盖国内大部分「能看图」的 API；换家只改预设 / Base URL / Model / Key，不改业务代码。

统一请求形态（Chat Completions + `image_url`）：

```text
messages[].content = [
  { "type": "image_url", "image_url": { "url": "data:image/jpeg;base64,..." } },
  { "type": "text", "text": "<结构化识图 Prompt>" }
]
```

实现要点：

1. **默认只走 OpenAI 兼容协议**（`openai` Python SDK + 自定义 `base_url`）。国内多数中转与官方兼容模式都吃这一套。
2. **图片优先 Base64 data URL**（不依赖公网图床）。部分厂商（如 Kimi 官方）明确不支持外链 URL，只认 Base64。
3. **厂商差异用 Adapter 钩子消化**（同一接口，少数特例）：
   - 是否允许 `detail` 字段；
   - 最大边长 / 体积限制（压缩到厂商上限内）；
   - 少数非标准字段（尽量避免；实在不行再加薄适配层）。
4. **设置页「视觉」卡内置预设**，一键填好 Base URL 与推荐模型，用户只贴 Key。
5. **「自定义」永远可用**：任意 OpenAI 兼容中转 / 自建 vLLM / OneAPI / New API 等。

#### 视觉预设表（MVP 内置，可扩展）

| 预设 ID | 名称 | 默认 Base URL | 推荐模型（可改） | 说明 |
|---------|------|---------------|------------------|------|
| `sensenova` | 商汤 SenseNova | `https://token.sensenova.cn/v1` | `sensenova-6.8-flash-lite`（亦可 `sensenova-6.7-flash-lite`） | OpenAI 兼容多模态；URL / Base64 识图。文档 [platform.sensenova.cn/docs](https://platform.sensenova.cn/docs) |
| `kimi` | Kimi / Moonshot | `https://api.moonshot.cn/v1` | `moonshot-v1-8k-vision-preview` 或官方最新 vision | 国内常用，识图稳；官方以 Base64 为主 |
| `qwen_vl` | 通义千问 VL | `https://dashscope.aliyuncs.com/compatible-mode/v1` | `qwen-vl-plus` / `qwen-vl-max` | 阿里云兼容模式 |
| `zhipu` | 智谱 GLM-V | `https://open.bigmodel.cn/api/paas/v4` | `glm-4v` / `glm-4.6v-flash` 等 | 性价比高，适合默认候选 |
| `siliconflow` | 硅基流动 | `https://api.siliconflow.cn/v1` | 控制台可选 VL 模型 | 聚合多家开源 VL |
| `doubao` | 豆包 / 火山方舟 | 控制台给出的兼容 Endpoint | 方舟多模态模型 | 预设填官方文档当前地址 |
| `openrouter` | OpenRouter | `https://openrouter.ai/api/v1` | 任选带 `:free` / VL 的模型 | 海外聚合，可选 |
| `openai` | OpenAI | `https://api.openai.com/v1` | `gpt-4o-mini` 等 | 国际对照 |
| `custom` | 自定义 OpenAI 兼容 | 用户自填 | 用户自填 | **覆盖一切中转与自建** |

> **关于 DeepSeek**：DeepSeek **官方托管 API 目前是纯文本，不能直接识图**。Joy 里 DeepSeek 放在「判断 / 起草」卡做主力（国内直连、便宜快）；识图请选 Kimi / 通义 / 智谱 / 硅基等 VL。若用户通过硅基流动等第三方托管了带视觉的 DeepSeek 变体，走 `siliconflow` 或 `custom` 即可，无需单独硬编码。

设置页文案需写清：「识图」与「起草」可以是两家不同的模型——例如 **智谱识图 + DeepSeek 起草**。

### 9.2 三张卡（可继承）

| 卡 | 用途 | 国内典型搭配 |
|----|------|----------------|
| **视觉 / 识图** | 图 → 结构化对话 | 商汤 SenseNova / Kimi / 通义 VL / 智谱 V / 硅基 / 自定义 |
| **判断** | 意图 / 风险 / 动作 | DeepSeek、Kimi 文本、通义文本；或继承视觉卡（同模型纯文本问） |
| **起草** | 3 条候选 | **默认推荐 DeepSeek 官网**；也可通义 / Moonshot / 自定义 |

规则：

- 三卡 Key / Base URL / Model **各自独立**；留空则按「起草 ← 判断 ← 视觉」顺序继承非空配置（文本卡不会继承视觉的「必须带图」行为，只继承 endpoint + key + 可改为文本模型 id 的提示）。
- 每张卡「一键连通测试」：视觉卡发 1×1 最小 JPEG + 短 prompt；文本卡发一句 ping。
- 「获取模型列表」：对支持 `/models` 的兼容端点拉列表供选择（失败则允许手填 model id）。

### 9.3 调用策略（省钱）

- 视觉：仅消息区裁剪图；最长边限制（如 1280）；可配置 jpeg quality；按厂商上限再压一次；
- 帧哈希未变 → 不调用；
- 仅 `other` 侧增量消息触发完整链路；
- 手动「分析一次」按钮始终可用。

## 10. 采集与微信适配（首期）

### 10.1 窗口附着

- 枚举顶层窗口，匹配进程名（如 `Weixin.exe`）与类名 / 标题启发式；
- 用户可在设置里「点选窗口」或下拉选择；
- 最小化时暂停采集并提示。

### 10.2 区域

MVP 可采用：

1. **整客户区送视觉**（实现快，费 token）；或  
2. **粗裁剪**：去掉标题栏 / 侧边栏的经验比例 + 设置里可调边距（推荐作为默认）。

精细像素锚点（jev 风格）放到 v0.2，作为「降低 Vision 费用」的优化，而非阻塞项。

### 10.3 差分

- perceptual / aHash 对比上一帧裁剪区；
- 无变化 → 跳过；
- 有变化 → Vision；解析后与会话缓冲做文本去重，仅新 `other` 消息触发 Analyze。

## 11. 填入策略

顺序：

1. 写入剪贴板；
2. 尝试将焦点落到目标窗口输入区（公开 API / 模拟点击输入框区域，需可配置、默认可关）；
3. 发送 `Ctrl+V`；
4. **禁止** `Enter` 作为「发送」；禁止点击发送按钮坐标（即使以后做 UI 自动化也默认关闭）。

任何 Fill 路径的单元测试需断言：不包含「发送」键绑定。

## 12. 隐私与合规（文档义务）

`docs/PRIVACY.md` 必须写清：

- 截了什么（哪类窗口、是否整屏）；
- 何时出网、发给哪些用户配置的域名；
- 发出去的字段（裁剪图、最近 N 条文本、关系与风格）；

## 14. 开发约定

1. **密钥**：禁止写入 `config.json` / 测试快照；CI 用 mock。
2. **日志**：禁止打印完整截图 base64、完整 Key、完整聊天原文（可打长度与 hash）。
3. **依赖**：Provider SDK 按需可选安装组（`joy[openai]` 等），核心保持精简。
4. **提交信息**：中英文均可，说明「为什么」；不强制 Conventional Commits。
5. **灵感致谢**：README / NOTICE 注明灵感来自 jev-chat，但代码独立实现，不复制其密钥处理与专有模型绑定逻辑以外的受版权保护的大段文本资源。
6. **Issue 标签建议**：`capture` / `vision` / `skill` / `privacy` / `packaging`。

## 15. 风险与对策

## 16. 成功标准（v0.1）

在 Windows 10/11 + 微信 4.x 上：

1. 用户配置任一可用视觉 API Key 后，打开单聊窗口，点「分析一次」；
2. 60 秒内悬浮窗出现意图摘要与 ≥2 条候选；
3. 点「填入」后文字进入输入框且消息未自动发出；
4. 暂停采集后不再发起 Vision / LLM 请求；
5. 仓库可克隆、`pip install -e .` 后按 README 跑通上述路径。
