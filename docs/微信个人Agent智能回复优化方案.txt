# 微信个人 Agent 智能回复优化方案

我把你给的**聊天截图 + agent 后台日志**一起看了。这个问题其实已经比较明显了：

> **你现在的核心问题，不是“模型不够聪明”，而是“每次回复都在重新理解这个群聊”，缺少一个真正的「对话状态机 + 回复去重 + 自己说过什么」层。**

所以它才会出现你说的三种典型症状：

**AI 味重、反常理、复读。**

而且从你的日志看，这几个问题基本已经能定位到架构层了。

---

# 一、先说截图：你的 AI 到底蠢在哪里

你这个群聊非常典型。

前面已经连续聊的是：

> 山上塌方 → 水库塌了 → 车冲下去了 → 有没有伤到人 → 是施工放炮导致的 → 水库被震塌了

但是你的 AI 回复路径是：

> “这图啥情况？看着有点吓人啊”  
> “这水库塌方看着真有点吓人，大家注意安全啊”  
> “卧槽这也太猛了，还好没伤到人吧”  
> “卧槽这也太吓人了吧，现场有没有人没事啊？”  
> “跟上次那个水库塌的有一拼了”

这不是单纯的“语言模型不够聪明”。

它实际上犯的是一个更底层的错误：

### 它没有判断“这个话题现在走到哪一步了”。

它每一次都在：

> 看到「水库塌了」  
> ↓  
> 自动生成一个“第一次听到这件事”的反应

所以你会觉得它像复读机。

真正的人类聊天不是这样。

人脑实际上一直在维护一个很小的状态：

```text
当前话题：水库塌方

已经知道：
- 山上塌方
- 水库塌了
- 有车被冲下去
- 目前不知道有没有人员受伤
- 后续有人说是附近施工放炮
- 又有人说自己刚从那回来
- 对方补充“不是大事”

我自己已经说过：
- 吓人
- 注意安全
- 有没有伤到人

所以：
下一条再来“水库塌了”
不能再次说“好吓人”
更不能再次问“有人受伤吗”
```

你现在显然缺的就是这个。

# 三、你现在最应该改的，不是 Prompt，而是 Memory 结构

这是我最想提醒你的。

你现在的 memory 如果主要还是：

```json
[
  {"speaker":"汤桓宇","text":"山顶上的水库塌了"},
  {"speaker":"我","text":"这水库塌方看着真有点吓人"},
  {"speaker":"汤桓宇","text":"这还一辆车让冲下去了"},
  ...
]
```

它实际上只是一个：

> **聊天记录仓库**

而不是：

> **对话记忆**

这两个东西差别非常大。

# 四、建议你把 Memory 拆成 5 层

我建议你的 Agent 后面直接按照这个思路重构。

## ① Recent Messages：最近原文

只保留最近，比如：

```text
最近 8~12 条
```

原文保存。

这是“短期工作记忆”。

---

## ② Topic State：当前话题状态

这是最重要的一层。

例如自动维护：

```json
{
  "topic": "水库塌方",
  "topic_status": "active",
  "facts": [
    "山顶水库发生塌方",
    "有车辆被冲下去",
    "有人认为是附近施工放炮导致",
    "目前有人说自己刚从附近回来",
    "目前没有确认人员伤亡"
  ],
  "latest_development": "有人补充可能是施工放炮导致",
  "open_questions": [],
  "already_discussed": [
    "事情很吓人",
    "是否有人受伤"
  ]
}
```

这样模型下一次看到：

> “山顶的水库塌了”

它不会再从 0 开始理解。

它会知道：

```text
这是旧话题，不是新事件。
```

# 五、第三层：Self Memory

这个对你这个项目特别重要。

你必须单独记录：

## “我刚刚说了什么”

例如：

```json
{
  "my_recent_replies": [
    "这图啥情况？看着有点吓人啊",
    "这水库塌方看着真有点吓人，大家注意安全啊",
    "卧槽这也太猛了，还好没伤到人吧",
    "卧槽这也太吓人了吧，现场有没有人没事啊？"
  ]
}
```

然后给模型一个硬约束：

```text
不要重复表达最近已经表达过的观点、情绪和问题。
```

甚至你可以不把完整文本都交给大模型。

本地先做一个：

### 回复指纹

例如：

```text
表达惊吓
关心人员安全
询问有没有伤到人
提醒注意安全
```

那么下一次：

```text
候选回复：
“这也太吓人了吧，没人受伤吧”
```

本地直接判：

```text
intent_similarity = 0.91
```

干掉。

这个东西我非常建议你做。

因为：

> **“防复读”没必要每次都花 LLM Token。**

本地就可以拦掉大量垃圾回复。

# 六、第四层：人物关系 Memory

你说你已经做了：

> 角色 + 其他群聊人员关系

但不要只做：


```json
    "frequent_topics": ["游戏", "日常", "事故", "猫"],

    "interaction_history": {
      "usually_responds_to_questions": false,
      "likes_joking": true
    }
  }
}
```

你这个项目其实真正有价值的东西不是：

> “一个 LLM 聊微信”

而是：

> **一个知道“这个群是什么气氛、这个人是什么说话方式、我刚刚说了什么”的 LLM。**

你应该给群聊加一个状态：

```text

玩梗
认真讨论
吐槽
信息转发
围观
连续刷屏

```

比如你这个截图前半段：

```text
 topic = 水库事故

 humor_allowed = true
```

到了后面突然开始：

> 车  
> 飞盘  
> 猫

那就应该自动：

```text

```

而不是一直背着前面的“水库塌方”记忆。

# 八、你现在有一个非常关键的架构问题：每次都让模型“决定一切”

从日志来看：

```text
OCR
↓
Vision
↓
Memory
↓
LLM
↓
candidate=3
```

这实际上把太多事情交给模型了。

我建议你改成：

```text
                 ┌─────────────┐
新消息 ────────→ │ Message Gate │
                 └──────┬──────┘
                        ↓
                是否值得处理？
                 /          \
               NO            YES
               ↓              ↓
            忽略          更新 Conversation State
                              ↓
                       是否需要回复？
                         /       \
                       NO         YES
                       ↓           ↓
                    不回复      生成候选
                                    ↓
                            本地反复读检测
                                    ↓
                            本地语气检测
                                    ↓
                            本地上下文合理性检测
                                    ↓
                              最终回复
```

这会比：

```text
新消息 → 大模型 → 你觉得该不该说 → 说啥 → 怎么说
```

稳定得多。

# 九、我建议你把“要不要回复”彻底从“生成回复”里面拆出来

这是非常关键的一步。

不要：

```text
请分析并生成一个合适的回复
```

应该变成：

## Stage 1：Decision

只负责：

```json
{
  "should_reply": true,
  "reason": "对方提出了新的信息",
  "message_type": "new_information",
  "topic": "水库事故",
  "novelty": 0.72,
  "requires_direct_response": false
}
```

注意：

这里甚至可以大量使用规则。

然后：

## Stage 2：State Update

```json
{
  "topic": "水库事故",
  "new_fact": "附近施工放炮可能导致水库受损",
  "conversation_progress": "cause_revealed",
  "previously_said_by_me": [
    "表达惊讶",
    "询问人员安全"
  ]
}
```

最后：

## Stage 3：Reply Generation

这一步模型才真正负责：

> “在现在这个聊天位置，像这个人一样说一句话。”

这样模型一下就轻松很多。

# 十、你现在最明显的问题之一：消息“重复分析”

你的日志里特别明显。

比如：

```text
17:00:32 山顶上的水库塌了
```

然后又：

```text
17:01:16 山顶的水库塌了
```

甚至前面已经出现过类似内容。

但是系统又完整走：

```text
OCR
→ vision
→ memory ingest
→ memory prompt
→ LLM
```

这就是浪费，而且会直接加剧复读。

你需要一个：

# Message Deduplication

至少三个层次。

### 1. Exact Dedup

```python
hash(message_text)
```

完全一样：

```text
山顶上的水库塌了
山顶上的水库塌了
```

直接视为旧消息，不重新触发。

---

### 2. Semantic Dedup

例如：

```text
山顶上的水库塌了
山顶的水库塌了
水库在山上塌了
```

Embedding 相似度高：

```text
> 0.90
```

就标记：

```text
same_topic_same_fact
```

不是新事件。

---

### 3. State Delta

这个甚至比 embedding 更有用。

比如：

```text
水库塌了
```

↓

```text
水库塌了 + 车被冲下去了
```

这不是重复，而是：

```text
new_fact = 车被冲走
```

所以：

```text
topic 不变
state 更新
```

而不是重新建一个对话。

你的日志里：

可以改成：

后面最高已经：


这已经足以导致：

> **模型思考的时候，群聊已经又变了两条。**

# 十二、你这里还有一个非常严重的点：LLM JSON 解析失败

日志：

```text
merged llm failed, fallback 2-step
```

而且返回的 JSON 本身已经坏掉了：

```json
{
  "intent": "回应群内关于水库塌方事件的最新解释，表达震惊与庆幸，并顺势关心现场情况",
  "need": "对陈相补充的"施工放炮"原因表示意外，同时延续对现场安全的关切",
  "suggested_action": "回复一条简短消息，表达对人为原因导致事故的惊讶，并再次确认人员安全",
  "risk": 1,
  "should_reply_now": true
}
```

`need` 字段里的引号直接把 JSON 搞坏了。

随后：

```text
fallback 2-step
```

然后：

```text
llm ≈ 6191ms
total ≈ 10172ms
```

这个地方我建议你马上修。

不要再：

```text
Prompt要求输出JSON
↓
字符串解析JSON
```

尽量使用 API 原生：

```text
structured output / JSON schema
```

如果你当前 API 不支持，就至少：

```text
Pydantic / jsonschema
```

做严格校验。

并且千万不要让模型输出这种：

```json
{
  "need": "对陈相补充的"施工放炮"原因..."
}
```

另外：

### 失败后不要直接进入“完整重新推理”

可以：

```text
JSON失败
↓
修复解析 / fallback deterministic parser
↓
只重试结构化决策
```

不要直接：

```text
再重新跑一次全套 LLM
```

否则延迟和不稳定都会放大。

# 十三、你现在最需要的不是“更长 Prompt”，而是一个真正的 Reply Policy

我给你一个适合你项目的规则框架。

## Reply Policy

### A. 不回复

满足任意：

```text
只是重复旧消息
只是附和
只是无明确对象的感叹词
别人已经连续多人回复
自己刚刚已经表达过相同观点
当前消息没有给自己留下自然接话点
```

### B. 极短回复

比如：

```text
卧槽
离谱
我去
真的假的
啊？
笑死
```

注意：

**不要每一条都“认真回答”。**

你现在最大的问题之一就是：

> 每条消息都像客服一样“认真响应”。

微信群不是客服系统。

### C. 普通回复

只有出现：

```text
新事实
新观点
直接问我
和我的个人经历相关
有人 @我
需要我接话
```

才生成：

```text
1句 / 2句自然回复
```

### D. 长回复

只有：

```text
别人明确问问题
讨论技术问题
让我解释
让我提供意见
```

才允许超过两句。

# 十四、还有一个非常重要的问题：不要让 Prompt 教模型“当一个活跃的群聊成员”

很多 Prompt 会写成：

> “你需要积极参与群聊，及时回应……”

这句话实际上非常危险。

模型会理解成：

> **无论如何我都得说点什么。**

于是就会出现：

> “这也太吓人了吧……”  
> “大家注意安全啊……”  
> “还好没人受伤……”  
> “确实挺危险的……”

这种典型 AI 话术。

你的 Prompt 应该反过来：

> **默认不回复。只有当回复会自然地推动当前对话时，才回复。**

这个改变非常大。

# 十五、你应该建立一个“AI 味黑名单”

不是简单禁词，而是：

## 禁止模式

### ① 总结型

```text

```

### ② 正能量型


你的真实群聊基本不需要这些。

### ③ 万金油型

```text

这也太夸张了
还好没事
真的有点吓人
```

这些词不是不能出现。

而是：

> **高频重复就应该降权。**

# 十七、候选 3 条没错，但你现在缺的是“候选淘汰器”

日志里有：

```text
cand=3
```

这说明你已经开始做候选生成了。

很好。

但是不要直接：

```text
LLM 生成三个
↓
LLM 选一个
```

建议：

```text
生成 3 个
     ↓
本地规则过滤
     ↓
重复度检查
     ↓
上下文一致性
     ↓
与最近自己回复相似度
     ↓
消息长度
     ↓
人物说话风格
     ↓
最终再让一个小模型做排序
```

比如：

```text
Candidate A
“这也太吓人了吧，没人受伤吧”

Candidate B
“原来是施工放炮搞出来的？”

Candidate C
“卧槽，这一下动静够大的”
```

本地反复读检测会直接发现 A 和你前面已经说过的东西太像。

这种方法会比“让大模型努力一点”稳定得多。

# 十八、我甚至建议你增加一个特别简单的指标：Novelty

每条消息进来先计算：

```text
novelty = 这条消息相对于当前话题新增了多少信息
```

例如：

```text
“山顶上的水库塌了”
novelty = 0.1
```

因为已经知道了。

---

```text
“车也被冲下去了”
novelty = 0.8
```

新事实。

---

```text
“应该是附近施工放炮”
novelty = 0.9
```

新因果解释。

---

```text
“卧槽”
novelty = 0.0
```

这种就很可能无需回复。

# 二十一、给你一个可以直接拿去改的核心 Prompt 思路

不是让模型：

> “根据上下文生成最合适的回复。”

而是：

```text
你正在模拟真实微信群聊中的一个普通成员。

你的第一任务不是回复，而是判断“现在是否自然地需要回复”。

必须遵守：

1. 默认可以不回复。
2. 不要重新总结已经聊过的事情。
3. 不要重复自己最近已经说过的观点、情绪、问题。
4. 对已经出现过的信息，不要再次表现得像第一次知道。
5. 优先回应“最新产生的信息”，而不是重复整个话题。
6. 如果当前消息只是附和、感叹、重复旧信息，可以不回复。
7. 不要为了表现活跃而强行接话。
8. 不要使用客服式、新闻播报式、总结式语言。
9. 不要主动提醒“注意安全”“希望大家平安”等模板化内容，除非上下文明确需要。
10. 回复长度应接近该成员真实聊天习惯。
11. 回复应该像聊天，而不是解释。
12. 如果没有自然接话点，输出 NO_REPLY。
```

但是我强调一下：

### Prompt 只是最后 30% 的东西。

你现在这种情况，继续疯狂改 Prompt，收益不会特别大。

**真正决定效果的是状态和记忆架构。**

# 二十二、你现在日志里暴露出来的性能问题

你的流程现在基本是：

```text
OCR 1~2s
Vision 2.5~3.4s
LLM 1.8~2.8s
```

最终一轮经常：

```text
5~6 秒
```

而异常时直接：

```text
10.172s
```

所以你最好再做一个：

## Generation Version

例如：

```python
conversation_version += 1
```

开始生成的时候：

```python
version = conversation_version
```

LLM 生成完：

```python
if version != conversation_version:
    discard()
```

意思就是：

> **我开始思考之后，如果群里又来了新消息，那么这次思考结果作废。**

这个功能对于实时微信群 Agent 特别重要。

否则很容易：

```text
17:00:32
对方：水库塌了

开始思考……

17:00:36
对方：原来是施工放炮

17:00:38
AI：这水库塌了看着真吓人……
```

用户当然会觉得：

> **这 AI 怎么跟不上人话。**

这几个变量一旦建立起来，你这个东西就会从：

> **“真的像群里某个人在聊天的 Agent”。**

而且你现在这个项目，我非常建议把 **“回复生成”与“对话状态管理”彻底拆开**。这是你目前最值得做的一次架构升级。
