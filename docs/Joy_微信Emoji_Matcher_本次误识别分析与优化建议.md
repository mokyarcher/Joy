# Joy 微信 Emoji Matcher：本次误识别分析与优化建议

## 1. 本次问题现象

本次真实测试中，对方实际发送的是：

```text
😍😍😍
```

对应微信标签应为：

```text
[色][色][色]
```

但当前 Matcher 日志得到：

```text
top3=[
    ('心碎', 0.61),
    ('嘴唇', 0.608),
    ('握手', 0.599)
]

pick=心碎
score=0.610
margin=0.002
conf=medium

se_rank=36
```

最终 Agent 上下文变成：

```text
[心碎][心碎][心碎]
```

而不是：

```text
[色][色][色]
```

---

# 2. 核心结论

这次问题不是：

> “最终评分把 `[色]` 误判成 `[心碎]`。”

更准确地说，是：

> **正确的 `[色]` 在前面的候选召回阶段就已经被淘汰了。**

日志里的：

```text
se_rank=36
```

非常关键。

它说明 `[色]` 在前面的初筛阶段只排到了第 36 名，因此后面的 Top 3 根本没有 `[色]`。

所以当前最应该修的不是单纯调整最终权重，而是：

```text
1. 候选召回
2. 图像裁剪/对齐
3. 背景影响
```

---

# 3. 为什么偏偏 `[色]` / 😍 容易出问题

当前模板：

```text
色.png
```

本身是正确的。

用户当前真实聊天截图里的：

```text
😍
```

也和模板属于同一个微信表情。

问题主要来自：

> **表情在截图中的实际位置、尺寸、空白区域，与模板裁剪位置并不是像素级一致。**

例如模板可能是：

```text
40×40

┌────────────────┐
│                │
│       😍       │
│                │
└────────────────┘
```

而聊天截图中的裁剪可能变成：

```text
40×40

┌────────────────┐
│                │
│         😍     │
│                │
└────────────────┘
```

即：

- 表情本体相同
- 但表情在裁剪框中的位置不同

对于简单的逐像素比较和 SSIM 来说，这个差异非常明显。

---

# 4. 当前算法的第二个问题：背景参与了匹配

当前输入并不是一张独立的：

```text
😍
```

而更接近：

```text
聊天气泡背景 + 😍
```

例如：

```text
┌──────────────────────┐
│                      │
│         😍           │
│                      │
└──────────────────────┘
```

如果直接对整个 40×40 做比较，那么大量像素实际上属于：

```text
聊天气泡背景
```

而不是表情本身。

于是可能出现：

```text
心碎.png
```

虽然表情内容完全不一样，但是：

- 背景颜色接近
- 大面积空白区域接近
- 整体亮度接近

最终仍然获得较高的综合分数。

这从当前日志可以明显看出来：

```text
心碎:
ssim  = 0.530
pixel = 0.867
edge  = 0.095
color = 0.974
```

尤其值得注意：

```text
edge = 0.095
```

轮廓相似度实际上很低，已经明显说明：

> `心碎` 的形状与真实目标并不像。

但是综合评分仍然让它排到了第一。

---

# 5. 当前算法暴露出的第三个问题：pHash 初筛过于强势

当前流程大致是：

```text
109
 ↓
pHash 初筛
 ↓
Top N
 ↓
SSIM
 ↓
综合评分
```

本次测试：

```text
真实答案：[色]

初筛排名：
色 → rank 36
```

这意味着：

> **如果初筛只允许 Top 15，那么 `[色]` 在第一阶段就永久消失。**

后面的 SSIM、Pixel、Edge 都没有机会再纠正这个错误。

---

# 6. 不应该让 pHash 决定生死

pHash 很适合：

> 快速召回。

但不适合：

> 作为最终淘汰规则。

推荐改成：

```text
109
 ↓
pHash Top 30
+
Edge Top 30
+
Color Top 30
 ↓
取并集
 ↓
Top 30~40
```

这样即使：

```text
色.png
pHash rank = 36
```

也不会因为单一特征失败而直接被淘汰。

---

# 7. 推荐的新版整体流程

建议：

```text
微信截图
    ↓
找到消息气泡
    ↓
找到表情候选区域
    ↓
扩大候选区域约 6~8 px
    ↓
前景提取 / 背景处理
    ↓
表情区域归一化
    ↓
pHash + Edge + Color 多路召回
    ↓
109 → Top 30~40
    ↓
平移对齐 + 尺寸微调
    ↓
Foreground SSIM
    ↓
Foreground Pixel
    ↓
Edge
    ↓
Color
    ↓
Top 5
    ↓
Top1 / Top2 Margin
    ↓
最终结果
```

---

# 8. 最重要的改进一：扩大原始裁剪区域

当前不建议：

```text
固定死 40×40
```

可以先：

```text
52×52
```

甚至：

```text
56×56
```

例如中心点：

```text
x, y
```

先裁：

```text
x-26 ~ x+26
y-26 ~ y+26
```

得到较大的候选区域。

理由：

> 让表情本体完整进入候选窗口，再由算法寻找真正的前景边界。

不要一开始就把表情紧紧裁死。

---

# 9. 最重要的改进二：寻找表情前景

应该从：

```text
背景 + 表情
```

中找：

```text
表情本体
```

可以建立：

```text
foreground mask
```

例如：

```text
┌──────────────────┐
│                  │
│      █████       │
│     ███████      │
│      █████       │
│                  │
└──────────────────┘
```

后续比较时：

```text
mask == foreground
```

区域权重高。

背景区域权重低甚至不参与。

---

# 10. 最重要的改进三：加入平移不变性

对于每个候选模板，不要假定：

```text
输入表情
和
模板表情
```

必须处于完全相同的像素位置。

可以允许：

```text
dx = -8 ~ +8
dy = -8 ~ +8
```

例如：

```text
for dx in range(-8, 9):
    for dy in range(-8, 9):
        score = compare(input, template shifted by dx/dy)
```

最终采用：

```text
max(score)
```

即：

> 在小范围平移中寻找最佳对齐位置。

---

# 11. 为什么平移搜索对这次 `[色]` 问题很重要

现在：

```text
色.png
```

和真实：

```text
😍
```

可能只是：

```text
位置偏移 2~5 px
```

但当前整图 SSIM 对位置非常敏感。

一旦加入：

```text
dx / dy 搜索
```

就有可能出现：

```text
未对齐：
SSIM = 0.53

偏移 +2,+3：
SSIM = 0.95+
```

此时 `[色]` 会重新成为明显的第一名。

---

# 12. 进一步加入轻微缩放搜索

微信截图过程中也可能出现尺寸差异：

```text
0.90
0.95
1.00
1.05
1.10
```

可以对 Top 10~15 候选做：

```text
scale × translation
```

搜索。

但不要对全部 109 张都这么做，否则没有必要。

---

# 13. 推荐新的候选召回方式

第一阶段：

```text
pHash Top 30
```

第二路：

```text
Edge Top 30
```

第三路：

```text
Color Top 30
```

然后：

```text
Union
```

最终得到：

```text
Top 30~40
```

例如：

```text
pHash:
色 = 36

Edge:
色 = 8

Color:
色 = 12
```

最终：

```text
色 ∈ Union
```

不会被单一 pHash 直接淘汰。

---

# 14. 推荐新的最终评分

当前：

```text
0.45 × SSIM
+
0.30 × Pixel
+
0.15 × Edge
+
0.10 × Color
```

对于存在聊天气泡背景的输入不是特别理想。

推荐改为：

```text
FinalScore
=
0.40 × ForegroundSSIM
+
0.25 × ForegroundPixel
+
0.25 × Edge
+
0.10 × Color
```

这里最重要的变化是：

```text
SSIM
```

和：

```text
Pixel
```

都优先比较前景，而不是整张截图。

---

# 15. Edge 应该获得更高地位

本次结果：

```text
心碎：
edge = 0.095
```

已经明显说明：

> 轮廓特征能够识别出它并不像目标。

因此 Edge 不应该只是很小的辅助项。

建议：

```text
Foreground SSIM = 40%
Foreground Pixel = 25%
Edge = 25%
Color = 10%
```

这样明显不符合目标轮廓的模板，即使背景颜色很像，也很难拿到第一名。

---

# 16. 对相似表情增加“局部区域匹配”

以下表情天然容易混淆：

```text
微笑
憨笑
奸笑
坏笑
愉快
笑脸
```

因此可以做：

```text
整体比较
 ↓
如果 Top1 / Top2 很接近
 ↓
比较局部
```

重点区域：

```text
眼睛
眉毛
嘴巴
特殊装饰
```

例如：

```text
Top1 = 奸笑
Top2 = 坏笑
```

进一步比较：

```text
嘴巴
眼睛
眉毛
```

通常能比继续做全图比较更有效。

---

# 17. 置信度不要只看 Score

需要同时：

```text
Top1Score
Top2Score
Margin
```

公式：

```text
margin = Top1Score - Top2Score
```

本次：

```text
Top1 = 0.610
Top2 = 0.608

margin = 0.002
```

这个结果其实已经明确告诉我们：

> 当前识别非常不确定。

所以当前系统正确地标记为：

```text
medium
```

但从 Agent 行为角度看：

> **medium 不能直接污染 Memory。**

应该进入二次识别。

---

# 18. 推荐置信度策略

初始工程阈值可以：

```text
score >= 0.92 且 margin >= 0.10
→ high
→ 直接采用
```

```text
0.80 <= score < 0.92
或 margin < 0.10
→ medium
→ 二次精匹配
```

```text
score < 0.80
→ low
→ VLM 兜底
```

阈值需要以后用真实微信截图测试集重新标定。

# 24. 对 Joy 的最终建议

当前阶段不要急着：

```text
训练深度学习模型
```

也不要：

```text
每条表情调用 VLM
```

先把：

```text
1. Crop
2. Foreground Mask
3. Multi-recall
4. Translation Search
5. Scale Search
6. Foreground SSIM
7. Edge
8. Margin
```

做好。

你的类别只有 109 个，这套工程化方案已经足够强。

---

# 25. 最重要的三项修改

如果只改三个地方，优先级建议：

### 第一

**pHash 不再单独淘汰候选。**

改为：

```text
pHash + Edge + Color
→ Union
```

### 第二

**加入前景提取，降低气泡背景权重。**

### 第三

**加入 ±8 px 平移搜索 + 轻微缩放搜索。**

这三个改完以后，再重新跑：

```text
😍
😍😍😍
```

这类真实聊天截图，才能判断算法的真实提升。

---

# 26. 最终原则

整个系统应该严格分成两层：

```text
Emoji Matcher
    ↓
“对方发的到底是哪一个表情？”
```

以及：

```text
Agent
    ↓
“这个表情在当前聊天中是什么意思？”
```

例如：

```text
Matcher：
[色]

Agent：
根据上下文判断是在表示喜欢、惊讶、调侃、看到有趣内容等。
```

不要让 Agent 反过来猜图片。

这次 `[色] → [心碎]` 的问题，本质上属于 **Matcher 视觉层问题**，不是 LLM 的语义理解问题。
